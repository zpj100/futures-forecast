## R1 · 从「电脑上的 WebView 壳」改造为手机本地独立 App

**用户原话（节选）**

> 首先对提示词进行优化，能够准确理解项目，节约 token，待我确认后执行（将此规则加入全局）。
> 将 futures-forecast 项目复制到本地 wsl 中修改，增加 app 手机内运行存储曲线数据，
> 自动每 30s 刷新下载数据（配置页面可以修改 5s、10s、30s、1min 等）、增加手动刷新数据功能，
> 页面布局方便手机查看，页面科技风格，可以通过底部标签切换功能，具备保存预测信息功能可以查询预测结果。
> 对应私有仓库为 https://gitee.com/zpj100/futures-forecast；做好 git 和版本管理。
> 手机 app 可以直接连接私有仓库发行版进行更新，其中个人令牌在 app 设置内自己输入后保存在手机端。
> 增加大模型预测功能，首先查询 github、gitee 开源期货预测与量化算法进行借鉴，给出分析建议，
> 大模型 api 可以在 app 设置中填写，计划采用 deepseek（可切换其他大模型）。

**核实到的现状**

原 APK 只是一个 `WebView` 壳，加载电脑上跑的本地 Web 服务；手机离开电脑就是白屏，
数据、曲线、预测全部来自服务端，App 自身没有任何存储与计算能力。

**方案（v2.0.0）**

| 需求 | 落地 |
|------|------|
| 手机内存储曲线 | SQLite（`ticks` 秒级点 / `kline` 多周期 / `forecasts` 预测留档 / `seed_meta` 预置库版本） |
| 自动刷新可配 | `Engine` 定时采集，5s / 10s / 30s / 1min / 5min，默认 30s；内置限流与失败退避 |
| 手动刷新 | 顶部刷新按钮 → 立即采集一轮并刷新 UI |
| 移动端科技风 + 底部标签 | 无框架 Canvas，4 个 Tab（行情 / 预测 / 历史 / 设置），CSS 变量统一主题 |
| 预测留档可查 | 每次预测落库，带 `due_at`，到期用实际价回填并统计方向命中率 |
| 自助更新 | 读 Gitee 私有仓库 `releases/latest`，比 `versionCode` 后下载 APK 并调起安装 |
| 令牌存手机 | `Cfg` 用 `SharedPreferences` + AndroidKeyStore 加密，仅本机 |
| 大模型预测 | `LlmClient` 走 OpenAI 兼容协议，默认 DeepSeek，BaseUrl / 模型名可在设置里改 |
| 开源算法借鉴 | `docs/06_算法借鉴.md`：vnpy（CTA 信号组织）、qlib（特征与标签）、backtrader（走前验证） |

**决策点（已确认）**：完全本地独立（不依赖电脑）＋ 一次做到 v2.0.0，不做过渡版本。

**构建环境**：WSL Debian + JDK 21 + Gradle 8.9 + `/opt/android-sdk`（android-34、build-tools 34.0.0），
脚本 `android/build-apk.sh`。

## R3 · 预置历史数据打包进 APK + 「同步历史数据」按钮

**用户原话**

> 将本地已经缓存的秒级点、分钟线、日线打包仅 sqlite 数据库和 apk 中。
> 设置-本地数据处增加同步历史数据按钮，可以同步最近 180 天分钟线、日线数据。

**核实到的数据边界**

- 新浪分时接口的 `type` 就是周期（1/5/15/30/60），**每个周期固定返回 1023 根**：
  1 分钟只有约 3 个交易日，60 分钟约 195 天 → 「180 天分钟线」只能由 60 分钟满足；
- 伦铝（`GlobalFuturesService`）忽略 `type`，只有当日分时 → 只能预置日线（2016 起）+ 当日分时；
- 秒级点公开接口**没有历史**，只能由 App 运行累积。

**方案**

`scripts/build_seed.py` 抓真实行情生成 `android/app/src/main/assets/seed.db`（1.5 MB / 19,487 根），
`SeedImporter` 用 `ATTACH DATABASE` + `INSERT OR IGNORE` 导入（不覆盖手机上更新的记录），
`.gitignore` 对 `seed.db` 开例外；设置页加「同步历史数据」→ `Engine.syncHistory()`。

**当时的口径**：同步按「近 180 天窗口」重拉并 `upsert`，属于整段覆盖式，后续在 R6 改为增量。

## R5 · 应用内更新报 HTTP 403，要求 Gitee 作为首要更新源

**用户原话**

> 下载失败http 403，要求将gitee作为首要更新仓库。

**根因（实测四种方式全部 403）**

| 尝试 | 结果 |
|------|------|
| 裸请求（浏览器 UA） | 403 |
| `Authorization: token xxx` | 403 |
| `?access_token=xxx` | 403 |
| 加 `Referer` 指回仓库页 | 403 |

私有仓库的 `releases/download/{tag}/{file}` 直链要**浏览器登录态 Cookie**；
而 `releases/latest` 的 `assets[]` 里既没有 `id` 也没有 `size`，拿不到可用路径。

**方案（v2.1.1）**：改走附件 API，并手动逐跳跟随 303

```
GET /api/v5/repos/{o}/{r}/releases/{id}/attach_files?access_token=      → attach_file_id + size
GET .../releases/{id}/attach_files/{fid}/download?access_token=        → 303 → foruda.gitee.com 签名地址
```

要点：`setInstanceFollowRedirects(false)` 手动解析 `Location`（≤6 跳，自动跳转丢 `token/ts`）；
令牌只放查询参数（CDN 段不认 `Authorization`）；下载后按附件 `size` 校验字节数，
不一致报「下载不完整」；401/403/404 分别给可读提示。更新源在代码里固定 `SOURCE_GITEE`。

> ⚠️ 装 v2.1.0 的用户更新器仍是旧代码，必须手动装一次 v2.1.1 才能自助更新。

## R6 · 覆盖安装后仍无本地数据，同步也不生效

**用户原话**

> 覆盖安装apk后仍然没有本地数据，行情页曲线处一直显示等待数据，预测等功能因显示数据不足。
> 需要将本机缓存的历史数据sqlite打包进入apk中，安装后直接使用。
> 点击设置中本地数据的同步历史数据无法更新数据，点击时需要实现与官方数据的增量更新。

**根因**：预置库一直在 APK 里，但**从未被导入过**。

```java
assetVer = Integer.parseInt(c.getString(0));   // "202611092054" 超 int 上限 → 抛异常
if (assetVer <= 0 || assetVer <= cfg.seedVersion()) return 0;  // 被吞成 0 → 永远在这里返回
```

`seed_meta.version` 是 12 位时间戳，`Integer.parseInt` 必然溢出 → 19,487 根 K 线一条都没进手机库，
所以曲线空、预测「样本不足」、点同步也看不到变化。

**方案（v2.1.2）**

- 版本号全面改 `long`（`Cfg.seedVersion` 用 `getAll().get()` 读 `Number`，兼容历史 int 值）；
- 自愈：本地 `kline` 为空就强制导入，不再只信版本号；版本号非法按 1 处理（宁可重导，不静默跳过）；
- ATTACH 失败自动退「逐行 ContentValues 批量写」兜底（个别 ROM 连接池导致 `no such table: seed.kline`）；
- 新增 `assets/seed_ver.txt` 旁文件，版本没变就不拷贝 1.5 MB；
- 同步改**增量**：查本地 `MAX(ts)`，只写「最后一根及之后」的 bar（boundary 那根 REPLACE 刷新），
  回显每周期 `added / total / incoming / error`；
- 本地库为空时启动 `autoSyncIfEmpty()` 自动补一次；
- `SinaClient.http` 加一次重试 + HTTPS 失败退 HTTP（个别 ROM 证书链问题）；
- 新增 `scripts/check_seed.py` 自检（导入模拟 + 幂等验证）。

## R7 · 1 秒 / 30 秒曲线、十字星、三品种同图、大模型七周期

**用户原话**

> 行情曲线页面增加1s、30s显示，点击时出现十字星时间标记，三个期货数据同时显示用不同颜色曲线标识。
> 大模型预测要求能够根据历史数据用deepseek大模型分析接下来1min、5min、15min、30min、4h、8h、1d的趋势，
> 给出趋势建议、目标区间。

**先出规格再执行**（按全局规则），三个决策点由用户拍板：

| 决策点 | 选项 | 结论 |
|--------|------|------|
| 1s 口径 | 原始采集点 / 增加 1 秒采集 / 两者都做 | **原始采集点**，界面如实标「采集点」，不假装 1 秒 K 线 |
| 三品种同图 | 窗口首点=0% 涨跌幅 / 归一化到 100 / 双坐标轴 | **窗口首点 = 0% 涨跌幅**，纵轴单位 % |
| 量化档位 | 一起对齐 / 只改大模型 | **一起对齐** 1m/5m/15m/30m/4h/8h/1d |

**方案（v2.2.0）**

- 数据层 `Store.tickSeries(code, bucketSec, limit)`：`bucket<=0` 取原始点（子查询倒序再升序，
  否则拿到的是时间窗**最早** N 条），`bucket=30` 按时间桶聚合成 OHLC；
- 图表从「按索引」重写为「按时间域」：多序列天然对齐，点数 > 900 等距抽样；
- 十字星：`pointerdown/move/up/cancel` + `setPointerCapture` + Canvas `touch-action:none`，
  竖线吸附最近点（二分），右侧价格气泡、底部时间、左上角 OHLC 浮窗，松手 2.5s 淡出；
- 单品种仍按红涨绿跌；对比模式用品种固定色（沪铝 `#4EA8FF` / 氧化铝 `#FFA63D` / 伦铝 `#B07BFF`），
  图例可点隐藏，避免涨跌色与序列色混淆；
- 量化 `Forecaster.HORIZONS` 改 7 档，4h/8h 由 60 分钟线聚合（走前验证步长改为 1 根）；
- `LlmClient` 重写：输入现价 + 7 档量化结论 + 指标 + 6 个周期统计 + 近 40 个采样点，
  输出固定 `horizons[7]`（方向 / 置信度 / 目标区间 / 依据）+ `overall / action / reasons / risks`，
  `normalize()` 补缺档、交换高低、单周期退化兜底；逐周期写 `forecasts`（`source='llm'`）。

**顺手修掉的仓库级隐患**：`.gitignore` 里的 `data/` 会匹配任意层级，把
`com/zpj/futures/data/`（`Engine` / `SinaClient` / `Products`）整个包挡在版本库外，
本地能编译、clone 下来缺类。改为 `/data/` 后补入，源码由 10 个变 13 个。

## R9 · 曲线实时跟随 + 数据增量落库 + 预测手动/整分刷新（v2.3.0）

**需求原文（2026-11-10）**

> 继续完成文档。优化行情曲线实时显示最新数据，增量查询到的最新秒级、分钟级数据自动增量添加到手机本地 sqlite 数据库，
> 设置中同步数据采用增量更新方式，预测页面增加更新按钮用于手动刷新预测（自动刷新预测规则为每个整数分钟、小时）。

**先确认的三个决策**

| 决策点 | 用户选择 | 取舍理由 |
|---|---|---|
| 自动预测频率 | 整分钟 + 整点加强 | 整分钟只重算短线四档（本地纯算术），整点才补数据 + 全七档，省电又不失时效 |
| 分钟线增量口径 | 1m 取最新几根 + 本地聚合 | 每轮只 3 个请求而不是 15 个，5/15/30/60 分钟口径天然一致 |
| 十字星与跟随 | 拖动时冻结、松手恢复 | 手指下的曲线不能跳，松手后再补上冻结期间的数据 |

**方案对照**

| 需求 | 之前的实现 | v2.3.0 的做法 |
|---|---|---|
| 曲线到最新 | 5 秒 `pull()` 重绘，但 1m 数据每 5 分钟才整段重拉 | 每 60 秒增量取 1m 最新几根；尾部再接一条「实时报价」点，曲线每个采集周期都走到现价 |
| 秒级增量落库 | 每轮 `saveTick` 一条，已是最小粒度 | 保持，并新增 `MAX(ts)` 边界去重，同一秒重复采集只覆盖不新增 |
| 分钟级增量落库 | `upsertKlines` 整段 1023 根 REPLACE | 只写 `ts >= 本地 MAX(ts)`；5/15/30/60 由本地 1m 按**时间桶**聚合后增量补 |
| 设置页同步 | 已按周期做 `MAX(ts)` 增量（v2.1.2） | 保持，文案与回显明确写「新增 X 根」；无新增时提示已是最新 |
| 手动刷新预测 | 无 | 预测页「更新预测」按钮：先增量补数据再跑全七档，带 3 步进度条 |
| 自动刷新预测 | 跟着采集线程顺带算，时间点漂移 | 独立调度器对齐 `:00` 秒；整分钟短线四档，整点补数据 + 全七档 |

**关键实现**

- `Store` 侧不再整段写：`Engine.incrementalMinute()` / `incrementalDaily()` 用 `lastKlineTs()` 做水位，
  只把「最后一根及之后」的 bar 交给 `upsertKlines()`（boundary 那根 REPLACE 刷新，保证未收盘的 K 线也在动）。
- 长周期不再向源站单独要：`Forecaster.aggregateByTime(1m序列, 分钟数)` 按
  `ts - ts % (分钟×60000)` 分桶，桶起点可被周期整除，避免「每 N 根一组」造成的错位。
- 预测分档：`Forecaster.forecast(..., prev, shortOnly)`，`shortOnly=true` 时 4h/8h/1d 直接深拷贝上一次结果，
  只有 1m/5m/15m/30m 重算；整点才 `shortOnly=false` 全量重算。
- 调度：`Engine.scheduleForecast()` 延迟到「下一个整分 + 300ms」启动，
  `scheduleAtFixedRate(..., 60s)` 保持相位；`(now / 60000) % 60 == 0` 判整点。
- 前端：`S.crossActive` 在 pointerdown 置位、松手 2.5s 后复位并 `renderChart()` 补刷新；
  图表脚注拆两行，第二行是`最新 价 · 时间`，超过 2 个采集周期没新数据标黄并写「滞后 N 秒」。

**自检**（`scripts/check_incremental.py`，复刻 Java 的边界筛选与分桶）

```
首轮：源站 1023 根 → 写入 1350 根 {'1m': 1023, '5m': 205, '15m': 69, '30m': 35, '60m': 18}
重跑：写入 5 根；总行数 1350 → 1350        ← 只有 boundary 一根被 REPLACE，零新增行
三分钟后：写入 9 根 {'1m': 4, '5m': 2, ...}  ← 3 根新 + 1 根 boundary
桶对齐与收盘价校验通过（60m 18 根）
```

**边界与未验证**

- 秒级仍只能来自本机 `ticks`：公开接口无历史，App 未运行时没有点。
- 息屏 / 切后台后系统可能冻结进程，整分钟调度会漏跑；回到前台会立刻补一次（`start()` → `computeForecast`）。
- 真机未验证：整点加强那一轮会多 3 个请求（每品种 1m + 日线），流量约 100 KB。

| # | 决策 | 理由 |
|---|------|------|
| D1 | 数据全部存手机本地，不依赖电脑 | 原 App 离电脑即白屏，是最核心的痛点 |
| D2 | 更新源固定 Gitee，GitHub 不作兜底 | GitHub 同名仓只到 v1.0.0，且源码含 keystore 口令，不宜公开 |
| D3 | 私有仓库只能用附件 API 下载 | 直链/CDN 需要浏览器 Cookie，四种鉴权方式实测全 403 |
| D4 | 秒级数据只来自本机累积，不伪造 | 公开接口无秒级历史，伪造会让用户误判 |
| D5 | 三品种同图用涨跌幅归一化 | 量级差 8 倍（20380 / 3126 / 2612），直接叠加会压成一条线 |
| D6 | 量化与大模型共用 7 档周期 | 便于互相印证，避免页面上出现两套不对齐的周期 |
| D7 | 包名 `com.zpj.futures` 永不改 | 改了老版本无法覆盖升级，用户需卸载重装会丢数据 |
| D8 | 大版本先出规格、确认后再改代码 | 避免按错误理解写几百行再返工（已写入全局记忆） |
| D9 | 分钟线用 `MAX(ts)` 水位增量，长周期由 1m 本地聚合 | 每轮请求从 15 个降到 3 个，各周期口径一致、可重入 |
| D10 | 预测整分钟只算短线四档，整点才全量 | 纯本地算术不必每分钟跑满，长周期档在 1 分钟内不会变 |
| D11 | 十字星按住期间冻结曲线跟随 | 手指下的曲线跳动会让人看错点位 |
