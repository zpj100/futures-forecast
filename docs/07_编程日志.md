# 编程日志

按时间倒序记录实现过程与踩坑，供后续维护参考。

## 2026-11-11 · v2.9.1 手机同步全量连续补齐（根治历史断点）

### 问题
手机端 1m+ 数据断点严重。根因：下行同步对 1m/5m/15m/30m/60m/1d 调用 `GET /api/db/sync3d`，该端点硬编码「最近 3 天」窗口，而服务端 `kline_native` 实际存有数周~数月的连续原生历史（AL 5m=1093 根/15天、30m=99天、60m=196天）。结果手机只拿到 3 天，老于 3 天全是断点。

### 修复
- `assets/app.js` 的 `dbSyncStart` 1m+ 下行分支：弃用 `sync3d`，改为对 `GET /api/db/export` 从 `since=0` 全量分页拉取（`has_more` 翻页直到 false），每页 300 根切片 `importBars` 幂等覆盖本地。服务端权威序列为准，彻底消除老于 3 天的断点。
- 1s/30s 维持本机实时采集真源、tail-only（`since=local_max`）。
- 服务端 `db_sync.py` 顶部 docstring 过期（写「5m+ 只读 kline_app」），实际已优先读 `kline_native`；修正注释并标注「手机 1m+ 全量补齐应走 export 分页，不要依赖 sync3d 的 3 天窗口」。

### 验证 / 边界
- 内盘 AL/AO 5m/15m/30m/60m：手机可拉到服务端全量连续历史（数周~数月）。
- 1m、外盘 AHD：受源站上限（getFewMinLine 固定 1023 根≈2.8 交易日）约束，历史天然仅约 2.8 天，非本 bug 范畴。
- 上传方向（uplink）未改；手机把本地 5m+ 回传 kline_app 为幂等冗余，无正确性问题。

## 2026-11-11 · v2.9.0 放开安卓 App 公网 HTTP 白名单（手机直连公网服务器同步）

### 做了什么

| 变更 | 实现要点 |
|------|----------|
| 放开公网 HTTP 白名单 | `Bridge.isValidServerBase` 的 http 分支新增显式放行：`h.equals("180.76.238.232")` 作为 `allowedPublic`，仅该固定公网 IP 可走明文 HTTP；其余公网 http 仍拒绝，loopback / 私有网段 / https 规则不变 |
| 配套发版 | 服务端 `/api/db/*`（status/export/sync3d/import）此前已具备手机双向同步能力（v2.6.0/v2.8.0），本次仅为客户端可达性解锁；生产服务器 180.76.238.232:8123 已实测四个端点可用 |

### 关键发现

1. **安卓 App 默认拒绝公网 HTTP**：`isValidServerBase` 对 http 仅允许 loopback 与私有网段（10./172.16-31./192.168.），公网 IP 直接 `return false`，导致 App 无法保存 `http://180.76.238.232:8123` 作为服务端基址（setServer 抛异常不保存）。手机浏览器访问网页端不受此限（浏览器不限制公网 HTTP）。
2. **https 分支本就放行任意合法主机**：`isValidServerBase` 对 https 无条件 `return true`（默认 HttpURLConnection 仍会校验证书，自签会被拒），故若要免改 App 走加密需真实 CA 证书。本次用户选择最小改动：仅放开该固定 IP 的明文 HTTP。

### 踩坑

1. **安全与可达性权衡**：明文 HTTP 仅对已知固定 IP 开放，数据敏感度低（行情 + 用户自选 K 线）；若服务器 IP 变更，需同步改 `allowedPublic` 并重打包。

## 2026-11-10 · v2.8.0 分钟级贴右边缘 + 原生多周期根治预测数据不足 + 近 3 天同步补缺

### 做了什么

| 变更 | 实现要点 |
|------|----------|
| 曲线贴右边缘（网页 + Android） | 网页端 `extendToNow(bars, price)`：分钟级以上末根距现在 >30s 则追加一根延伸点（实时价优先、否则末收盘），`drawSingle/drawCompare` 文案区分「现在」；Android `loadBars` 同步加固：非 tick 周期末根 >30s 平铺延伸，tick（1s/30s）仅补更新鲜实时尾点 |
| 固定近 3 天比对窗口 | 1s/30s 仍只拉尾部（tail-only），仅 1m+ 做全量比对、只补缺 |
| 原生多周期落库（根治） | 后端 `collector._fetch_native` 对三品种内盘（AL/AO）用 Sina 原生 `fetch_minute(code, step)` 直采 5/15/30/60m 入 `store.kline_native`（step∈5/15/30/60），不经 1m 聚合；`forecaster.forecast_one` 分钟档优先取 native（≥_MIN_SAMPLES+step+10）兜底聚合；AHD 外盘原生只返当前时段不回溯，4h 无原生源如实保留「数据不足」 |
| 刷新预测按钮（网页） | 新增 `POST /api/forecast/refresh`（复用 `collector.state` 最新序列含 native，重算七档、写回 state、落库 forecast_log），预测面板加「刷新预测」按钮 |
| Android 同步近 3 天补缺 | 新增 `GET /api/db/sync3d`（服务端权威近 3 天整段切片，非分页）；Android `dbSyncStart` 下行 1m+ 改走 sync3d 幂等 `importBars`（按 300 切片分批以兼容 `importBars` 单次上限），1s/30s 维持 tail-only |

### 关键发现

1. **Sina 原生分钟接口内盘（AL/AO）对任意 period=5/15/30/60 均返回 1023 根**，回溯数周~数月；外盘（AHD）原生分钟仅返当前交易时段（~661 根，不回溯）。故原生直采只对内盘做，根治预测 5m/15m/30m 样本不足；4h 无原生源只能保留「数据不足」。
2. **`importBars` 单次上限 300 根**：sync3d 一次可能返回 >300（如 1m 近 3 天约 700+），必须在 JS 侧按 300 切片分批写入，否则整批被拒（返回 -1）。
3. **`1d` 的 `step` 为 0 而非 >1**：分类分钟级与否必须用 `isTick(period)`（tick 字段是否存在），不能靠 `step>1`，否则日线会被误判为秒级。

### 踩坑

1. **sync3d 超 300 根整批被 `importBars` 拒**：初版直接整段传入，1m 切片 ~720 根触发 `arr.length() > 300 → return -1`，手机本地 1m 缺口全失败；改为 300 切片循环后解决。
2. **`1d.step===0` 误分类**：首版用 `period.step > 1` 判分钟级，导致日线进入秒级分支；改用 `isTick()` 后正确。

### 做了什么

| 变更 | 实现要点 |
|------|----------|
| 更名「学记期货」 | `strings.xml` 改 app_name；页头与关于页同步；包名保持 `com.zpj.futures`，否则老版本无法覆盖升级 |
| 新图标 | `scripts/make_icons.py` 用 PIL + 微软雅黑粗体生成各密度 PNG：深色底 + 白色圆角方框 + 双行小字；自适应图标前景改用 `@mipmap/ic_launcher_fg`，删掉原矢量折线 |
| 白天模式 | CSS 全量变量化，`html.light` 覆盖一套亮色；`Cfg.theme` 持久化，`Bridge.setTheme` 同时改原生底色与状态栏图标；`<head>` 内联脚本先定主题，避免首屏闪白 |
| 行情页一屏 | 品种卡从横向滚动改 `grid-template-columns: repeat(3,1fr)`；图表 210→178px；指标卡收紧 |
| 多周期 K 线 | `kline` 表按 `period` 存 `1m/5m/15m/30m/60m/1d`；图表先读本周期，缺数据才用 1m 现场聚合 |
| 预置数据 | `scripts/build_seed.py` 抓真实行情生成 `assets/seed.db`（约 1.5 MB / 1.9 万根）；首次启动 `SeedImporter` 用 `ATTACH + INSERT OR IGNORE` 导入，不覆盖手机上更新的记录 |
| 同步历史 | 设置页「同步历史数据」→ `Engine.syncHistory()`：日线近 180 天 + 各周期分钟线（源站每周期 1023 根，60 分钟线≈195 天） |

### 关键发现

1. **新浪分时接口的 `type` 就是周期**：`type=1/5/15/30/60`，每个周期都返回 1023 根。
   实测 60 分钟线从 4 月底开始 → 约 195 天，正好能覆盖「最近 180 天分钟线」；
   而 1 分钟只能回溯 3 个交易日，所以「180 天 1 分钟」在公开源上不可能拿到，只能如实标注覆盖天数。
2. **伦铝（`GlobalFuturesService`）没有多周期历史**：`type` 参数被忽略，只返回当日分时（约 580 根）。
   因此伦铝只能预置日线（2016 起 2537 根）+ 当日分时，同步时也只拉这两类。
3. **秒级点无法预置**：公开接口不提供历史秒级数据，库里留空，由 App 运行后自行累积
   （`store.prune(30)` 保留 30 天）。不做「用分钟线伪造秒级点」，否则会污染后续统计。

### 踩坑

1. **Headless 截图里标签高亮「跑偏」**
   点击标签后 `.tab.active` 明明切换了，截图却还是旧颜色。原因是 `.tab { transition: color .18s }`：
   `--screenshot` 在 load 事件后立刻抓帧，动画还没跑完。加
   `@media (prefers-reduced-motion: reduce) { * { transition: none !important; animation: none !important; } }`
   并给 Chrome 加 `--force-prefers-reduced-motion` 后截图才准。这是截图工具的问题，不是 App 的 bug。
2. **浅色主题下 `.btn.ghost` 被实心按钮覆盖**
   `html.light .btn` 的优先级高于 `.btn.ghost`，导致「清除 Key」变成实心青色。补 `html.light .btn.ghost` / `.btn.danger` 显式覆盖。
3. **`*.db` 被 .gitignore 挡住**
   预置库要入库，必须加 `!android/app/src/main/assets/seed.db` 例外，否则 APK 里没有 assets。
4. **`ATTACH DATABASE ?` 在部分 ROM 上不稳**
   改成把路径转义后拼进 SQL（`'` → `''`）；导入用 `INSERT OR IGNORE`，保证手机上已有的新数据不被预置包覆盖。

## 2026-11-09 · v2.0.0 手机端独立化

### 目标

原 APK 是 WebView 壳，必须连电脑上的 FastAPI 才能用。v2.0 把采集、存储、计算、预测全部搬进手机，
后端降级为研究工具。

### 关键决策

| 决策 | 取舍 |
|------|------|
| 前端仍用原生 JS + Canvas | 无构建链，改完直接进 assets，APK 只 2.3 MB |
| 不用本地 HTTP 服务（NanoHTTPD） | 直接走 `@JavascriptInterface` 桥，少一个端口与生命周期问题 |
| 不做在线岭回归 | 手机上训练 11 维岭回归收益极低，只移植信号库 + 走前验证 |
| 指标/预测口径与 Python 版对齐 | 便于对照两边结论，出问题能定位是谁错 |

### 踩坑记录

1. **新版 cmdline-tools 的 `sdkmanager` 会崩**
   报 `AccessDeniedException: /opt/android-sdk/.sdk/lock`。原因是它已被标记 deprecated，
   改由 `android sdk --sdk=<path> install ...` 接管；同时 `/opt/android-sdk` 之前被 root 写过，
   要先 `chown -R $USER`，否则锁文件永远拿不到。

2. **Gradle 8.2.1 不支持 JDK 21**
   Debian 13 仓库没有 openjdk-17，只能升 Gradle 到 8.9（JDK 21 从这里开始正式支持）。
   `android/build-apk.sh` 已同步改成 8.9 + 自适应版本号产物名。

3. **`JSONArray.put` 会抛受检异常**
   `Engine.sparkline()` 里两处 `put` 没包 try/catch，javac 直接报
   `unreported exception JSONException`。整个方法体包一层 try 即可，不要逐行加。

4. **`ScheduledExecutorService` 不能复用**
   改刷新间隔时若只 `shutdownNow()` 再 `schedule()`，会抛 `RejectedExecutionException`。
   必须整体替换实例：新建 → 旧实例 shutdown → 重新排程。

5. **CSS Grid 的 `1fr` 会被内容撑破**
   `repeat(3, 1fr)` 在窄屏上会被 min-content 撑开，导致整页横向溢出、底部第 4 个 tab 看不见。
   全部改成 `repeat(n, minmax(0, 1fr))`，并给数值单元加 `text-overflow: ellipsis`。

6. **headless Chrome 截图不可信**
   Windows 显示缩放 125% 时，`--window-size=390,844` 截出来的是 487 CSS px 的页面左半边，
   看起来像"右侧被裁"，实际是截图工具问题。验证移动端布局要用「固定宽 iframe + 按比例放大窗口」，
   或直接用 DevTools 协议设 `deviceMetrics`。

7. **Gitee 私有仓库的 Release 需要令牌**
   `/releases/latest` 与 APK 下载地址都必须带 `access_token`。客户端把令牌存
   AndroidKeyStore 加密后的 SharedPreferences，不落明文、不上传服务器。

### 待办 / 已知限制

- 无真机回归：本轮只做了编译 + 静态 UI 截图验证，未在 Android 设备上跑过完整链路。
- 秒级历史只能从首次启动开始积累，`ticks` 表保留 30 天。
- 外盘（伦铝）分钟线仅当日，跨日依赖日线。
- 大模型分析的命中率需要跑一段时间才有统计意义。

## v2.1.1（修复应用内更新 403）

### 现象

手机端点「立即更新」提示「下载失败：HTTP 403」，`curl` 复现：

```
GET https://gitee.com/zpj100/futures-forecast/releases/download/v2.1.0/futures-forecast-v2.1.0.apk
→ 403 {"status":403,"data":null,"message":"403 Forbidden"}
```

### 根因

Gitee **私有**仓库的发行版直链要浏览器登录态 Cookie，任何机器人式访问都 403。逐一验证无效：

| 方式 | 结果 |
|------|------|
| 裸请求 / 带浏览器 UA | 403 |
| `Authorization: token xxx` 头 | 403 |
| `?access_token=xxx` 查询参数 | 403 |
| 加 `Referer` 指回仓库页 | 403 |

`releases/latest` 返回的 `assets[].browser_download_url` 就是这个下载不了的直链，
而且 `assets` 里**没有 id、没有 size**，无法据此换路径。

### 解法

改走「发行版附件 API」，这条路是带令牌可用的：

```
GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files?access_token=xxx
    → [{"id":3644410,"name":"...apk","size":3104666, ...}]

GET /api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files/{id}/download?access_token=xxx
    → 303 Location: https://foruda.gitee.com/attach_file/<hash>/<name>.apk?token=...&ts=...
    → 跟随即得 APK（3,104,666 字节，md5 与本地产物一致）
```

要点：

1. **附件 id 要二次请求**。`releases/latest` 不带 id，必须先拿 `release_id`，再查 `attach_files` 列表。
2. **必须手动跟 303**。`HttpURLConnection` 自动跳转在跨域时行为不可控，且 `followRedirects=true`
   会把 `Location` 里的 `token/ts` 查询参数丢掉；改成 `setInstanceFollowRedirects(false)`
   逐跳解析 `Location`（上限 6 跳），才稳定拿到最终 CDN 地址。
3. **令牌放查询参数**，不放请求头（CDN 段不认 `Authorization`）。
4. **体积校验**。附件列表给了 `size`，下载后比对，不等就报「下载不完整」，
   避免把半截 APK 交给系统安装器；另加 `<64KB 视为非安装包` 的兜底。

### 顺带改动

- 更新源在代码里固定为 **Gitee 首要源**（`Updater.SOURCE_GITEE`），界面显示「发现新版本 v2.1.1（3.0 MB · Gitee）」；
  将来若加镜像站只能做 Gitee 失败后的兜底，不得抢占首位。
- 错误提示细化：401 令牌无效 / 403 无权限 / 404 发行版或附件已删。
- 版本 `2.1.1` / `versionCode 211`。

### 教训

Gitee 的「发行版」在私有仓库下的对外下载链路，与公开仓库不是一套东西：
公开仓库直链可用，私有仓库只有 API 附件接口可用。文档里写的 `browser_download_url`
在私有场景基本是装饰品，别拿它当下载地址。

## v2.1.2（预置库没导入 · 同步改增量）

### 现象

覆盖安装 v2.1.1 后：行情页曲线一直「等待数据」，预测全部「数据不足」，
设置里「同步历史数据」点了也没变化。APK 内 `assets/seed.db` 确实存在（1.49MB / 19487 行）。

### 根因一：版本号 int 溢出，预置库永远不导入

`assets/seed.db` 的 `seed_meta.version` 是构建时的 12 位时间戳 `202611092054`，
而 `SeedImporter` 用：

```java
assetVer = c.moveToFirst() ? parseInt(c.getString(0)) : 0;   // Integer.parseInt!
if (assetVer <= 0 || assetVer <= cfg.seedVersion()) return 0; // ← 永远走这里
```

`Integer.parseInt("202611092054")` 抛 `NumberFormatException`（> 2,147,483,647），
被 `parseInt()` 的 catch 吞成 **0**，随后 `assetVer <= 0` 直接 return 0 ——
**1.9 万根 K 线一次都没进过手机库**。`Cfg.seedVersion()` 存的也是 int，同样有隐患。

修复：

- 版本号一律 `long`；`Cfg.seedVersion()` 用 `getAll().get(key)` 取 `Number`，兼容历史 int 值。
- 加**自愈**：本地 `kline` 为空就强制导入一次，不再只看版本号。
- 版本号异常（非数字）时按 1 处理，宁可重导一次也不要静默跳过。
- 导入后写 `seed_imported_at`，日志打印「新增/共 X 行」。

### 根因二：同步只写不报，看不出发生了啥

旧 `syncHistory` 把每步异常都 `catch` 掉只记品种名，成功时也只回「日线 5313 根…」，
用户无法判断是「没网」「源站限流」还是「压根没跑」。

现在：

- **增量合并**：先查本地 `MAX(ts)`，只写「最后一根及之后」的 bar（boundary 那根 REPLACE 刷新），
  重复点击不重复写库；返回值带每品种每周期的 `added / total / incoming / error`。
- 结果文案：`新增 42 根 · 本地 日线 8671 · 60分 2046 · 30分 2046 …`，
  失败追加 `部分数据未取到：沪铝60分钟[HTTP 403] …`。
- 摘要落 `Cfg.last_sync_msg`，`state()` 回传，设置页长期回显（关掉 App 也还在）。
- 本地库空时启动自动补跑一次（`autoSyncIfEmpty`），不依赖用户手动点。

### 顺带

- `SinaClient.http()` 加一次重试 + HTTPS 失败退 HTTP（源站两种协议都通）：
  个别 ROM 证书链过期或代理劫持会让 HTTPS 直接失败，退 HTTP 能救回来。
- `assets/seed_ver.txt`（构建时由 `build_seed.py` 写入）先比版本，命中就不再拷贝 1.5MB 的 seed.db。
- `importByAttach` 失败自动退「逐行 ContentValues 批量写」兜底，避免某些 ROM 连接池导致
  `ATTACH` 与 `INSERT` 不在同一连接（报 `no such table: seed.kline`）。
- 新增 `scripts/check_seed.py`：校验 seed.db 与 seed_ver.txt 一致、各周期覆盖天数、
  并模拟「建空库→ATTACH 导入→按 App 的 SQL 取数」，19487 行可完整导入且二次导入幂等。

## v2.2.0 行情曲线交互 + 大模型七周期（2026-11-09）

需求确认后的三个决策：1s 用「原始采集点」而不是假装 1 秒 K 线；三品种同图用
「窗口首点 = 0% 涨跌幅」归一化；量化模型档位同步对齐大模型的 7 档。

### 秒级曲线只能来自本机 ticks

`ticks` 表每采集一次写一条（默认 30 秒），`seed.db` 里 `ticks=0`，公开接口也没有
秒级历史。所以 `1s` 与 `30s` 都走同一套 `Store.tickSeries(code, bucketSec, limit)`：

- `bucketSec <= 0` → 原始点（`o=h=l=c=price`），SQL 用子查询 `ORDER BY ts DESC LIMIT n`
  再外层升序，否则取到的是时间窗**最早**的 n 条而不是最新 n 条；
- `bucketSec = 30` → 按 `ts / (30*1000) * (30*1000)` 分桶，桶起点作为时间戳，聚合成 OHLC + 计数；
- 时间窗按 `bucket * limit * 2` 截断（30 秒 × 600 桶 ≈ 10 小时），避免 30 天 ticks 全表扫；
- 只保留尾部 `limit` 个桶。

前端在 `loadBars()` 里按 `period.tick !== undefined` 分流，其余周期仍走 `N.kline`。

### 图表从「单线 + 按索引」重写为「多序列 + 按时间」

旧实现 `X(i) = padL + i/(n-1)*width`，三条序列时间点不一致时会对不齐，也没法做时间十字星。
现在：

- x 轴域取所有序列 `min(ts) ~ max(ts)`，不同品种/周期天然对齐；
- 对比模式把每点换算成 `(c/base - 1) * 100`，`base` 是该序列窗口首点；
- 纵轴 4 条网格 + 右侧刻度，对比模式刻度带 `%`，横轴三点时间（左/中/右），
  秒级周期显示 `HH:mm:ss`；
- 点数 > 900 时等距抽样（十字星吸附按抽样后的点，误差 ≤ 1 根）；
- 单品种沿用红涨绿跌 + 渐变填充 + 现价标签；对比模式用品种固定色

## 2026-11-09 · v2.2.1 下载与同步进度条

### 做了什么

| 位置 | 之前 | 现在 |
|------|------|------|
| 应用更新下载 | 点完只有 toast，不知道进度 | `Updater.Progress` 回调 → `onUpdateProgress`，进度条 + `1.5 / 3.0 MB` + 百分比；按钮实时变「下载中 51%」 |
| 历史同步 | 一行「同步中…」 | `SyncListener` 带 `done/total`，按「品种 × 周期」14 步推进，条上写「同步 氧化铝 15分钟…（8/14 步）」 |

### 实现要点

**总长度从哪来**：下载连接先 `getContentLengthLong()`（3xx 手动跟随后的 CDN 响应有 `Content-Length`），
拿不到就用 `checkUpdate` 时记下的附件 `size`（`installUpdate(url, version, size)` 三参传入——
之前 `Bridge` 里 new 的 `Info` 只有 url 和 version，没有 size），两者都没有才退「不确定态」。

**节流**：下载循环里最多 5 次/秒回调（`now - lastAt >= 200 || total - lastBytes >= 512*1024`）。
每次回调都会跨线程 `evaluateJavascript`，不节流会让 WebView 主线程排队、反而拖慢下载。

**四个阶段**：`start / downloading / done / error`。`error` 不隐藏进度条，而是变红并保留已下载量，
同时把按钮从禁用的「下载中」恢复成可点的「重试更新」——用户不用再去点「检查更新」。

**不确定态**：`.prog.indet > i` 用 `!important` 的 38% 宽度 + `translateX` 动画；
`prefers-reduced-motion` 下关掉动画并改成半透明满格（否则静止时看起来像"卡在 38%"）。

### 踩坑

1. `.prog-wrap` 用 `hidden` 属性控制显隐，但 CSS 里同类选择器给了 `display` 就会盖掉 `[hidden]`，
   必须显式写 `.prog-wrap[hidden] { display: none; }`。
2. 一开始 `onSyncStep` 既写 `#syncInfo` 又写进度条，同一句「同步 氧化铝 15分钟…（8/14 步）」
   在界面上出现两行。改为步骤文案只进进度条，`#syncInfo` 在同步过程中保持固定说明，完成后再写摘要。
3. `SyncListener` 的 `done` 是**已完成步数**（请求前回调时还是 0），界面上要 `done + 1`；
   最后一步「写入本地库并刷新…」传 `total/total`，让进度条在写库阶段保持满格。
4. 同步完成时 `onSync` 里的文字会被紧接着的 `pull()` → `renderSettings()` 覆盖成
   「上次同步 xx:xx：<摘要>」，属于预期（摘要里已含新增根数），不要以为是没生效。

### 验证

- Gradle `BUILD SUCCESSFUL`，`versionCode=221` / `versionName=2.2.1`；
- 无头 Chrome 模拟 `window.FF.onUpdateProgress()` / `onSyncStep()` 六种状态截图（暗色下载中 / 未知长度 /

## 2026-11-10 · v2.3.0 实时跟随 + 增量落库 + 预测定时

v2.2.1（进度条）构建后未发布，与本轮一起并入 v2.3.0，避免让用户连装两个包。

### 之前的问题

1. 图表每 5 秒重绘，但 `Engine.doRefresh` 里 1 分钟线是「每 5 分钟整段重拉 1023 根再 REPLACE」，
   曲线最多比现价慢 5 分钟；且 `klineCache` 整表替换，长周期更久才动。
2. 采集只写 `ticks`，分钟级数据完全靠整段覆盖，谈不上「增量」。
3. 预测是在采集回调里顺带算的，时间点跟着刷新间隔漂移，没有「整分钟」概念，也不能手动触发。

### 改法

**分钟线增量 + 本地聚合**（`Engine.incrementalMinute` / `incrementalDaily`）

- 水位：`store.lastKlineTs(code, period)`，只把 `ts >= 水位` 的 bar 交给 `upsertKlines`，
  boundary 那根被 REPLACE 刷新，所以「正在走的 K 线」也能实时变。
- 5/15/30/60 分钟不再向源站单独请求：用本次的 1m 序列 `Forecaster.aggregateByTime(m, N)` 聚合，
  再按各自水位增量补。每轮请求 3 个（每品种 1 个）而不是 15 个。
- `mergeCache()` 把增量并入内存缓存，不整表重读（同 ts 覆盖、尾部追加、超长裁头）。
- 日线单独降频到 30 分钟一次（日线一天只变一次，没必要每轮拉）。

**时间桶聚合**（`Forecaster.aggregateByTime`）

旧实现 `aggregate(src, group)` 是「每 N 根一组」，首根不对齐时 4h/8h 会落在 03:47 这种奇怪时刻。
现在按 `ts - floorMod(ts, 周期毫秒)` 分桶，桶起点必被周期整除。自检里专门断言了这一点。

**预测调度**（`Engine.scheduleForecast` / `tickForecast`）

- 启动时算 `delay = 60000 - (now % 60000) + 300`，对齐到下一个整分；之后 `scheduleAtFixedRate(60s)` 保持相位。
- 整分钟：`computeForecast(false)`，只重算 1m/5m/15m/30m 四档；4h/8h/1d 从上次结果深拷贝（`Forecaster.reuse`）。
- 整点（`(now / 60000) % 60 == 0`）：先 `incrementalMinute(true)` + `incrementalDaily(true)` 补数据，
  再 `computeForecast(true)` 全量七档。
- 手动：「更新预测」→ `forceForecast()`，补数据 + 全七档 + 回填到期，3 步进度条走 `onPredictStep`。
- 采集线程和调度线程可能同时进增量逻辑，三个方法都加了 `synchronized`，避免同一批数据被取两次。

**曲线跟最新**

- `loadBars()` 末尾把最新报价接成一条点（`[quote.ts, last, last, last, last, 0]`）：
  K 线只到上一根收盘，不接的话曲线永远比现价慢半拍。1s/30s 走 `ticks`，本身已含现价，不重复接。
- `S.crossActive`：pointerdown 置位后 `pull()` 不再 `renderChart()`；松手 2.5 秒复位并主动 `renderChart()`，
  把冻结期间到的数据一次补上。这样手指下的线不跳，松手也不丢新点。
- 脚注拆两行：第一行周期/点数/起止，第二行`最新 价 · 时间`；超过 `max(2×刷新间隔, 2 分钟)` 没新数据标黄并写「滞后 N 秒」，
  日线不参与滞后判断（日线的 ts 是交易日期，天然「滞后」）。

### 踩坑

1. `Math.floorMod(long, long)` 而不是 `%`：虽然 ts 是正数两者等价，但用 `%` 在时区/夏令时换算场景下容易写错。
2. 伦铝不能聚合长周期：`SinaClient.minute("AHD")` 忽略 type 只返回当日分时，
   聚合出来 60 分钟只有 4 根，图上像坏掉。保持「1m + 日线」。
3. 预测 `shortOnly` 复用长周期档时必须是深拷贝（`new JSONObject(h.toString())`），
   直接引用会让上一轮对象被下一轮覆盖，历史记录跟着变。
4. 手动刷新完成后 `pull()` 会重写 `#predInfo`，把「新增 X 根」覆盖成「尚未更新」——
   在 `onPredict` 里先回填 `S.state.last_forecast` 再 `pull()`，两条信息才不会互相打脸。

- `python3 scripts/check_incremental.py`：首轮 1023→1350 行、重跑零新增、三分钟后 4 根增量、

## v2.4.0 · 同步前体检 + 更新全链路进度条

### 一、同步先体检（Engine.syncHistory）

老同步只有 `tail(bars, localMax)`：只补「本地最后一根之后」。中间被挖掉一段、或某周期整段被清空，
它永远发现不了，也不会补。v2.4.0 把同步拆成三段：

1. **体检**：每个「品种 × 周期」拉一次源站数据并缓存（写入阶段复用，不重复请求），
   逐根比对本地时间戳。判据只有两条：
   - 源站有、本地没有，且时间戳**早于本地最后一根** → 空洞（`missing`），连续空洞算一段（`gaps`）；
   - 源站有、本地没有，且**晚于本地最后一根** → 正常尾部新增（`tail`），不算异常；
   - 本地近 7 天一根都没有而源站有 → 整段被清空（`cleared`）。
2. **补齐 / 增量**：`heal = missing > 0 || cleared || forceFull`，为真时把近 7 天窗口整体
   `INSERT OR REPLACE` 写回（空洞、尾部、边界行一次覆盖）；为假时走原来的 `tail` 增量。
3. **收尾**：秒级体检 + `reloadCaches()` + 统计。

**为什么以源站序列为基准**：商品期货有夜盘、周末、节假日，自建交易日历要维护一堆例外，
漏一个就把正常休市判成缺失。用「源站给了什么、本地有没有」逐根比对，天然免疫这些情况。

**为什么把「尾部新增」从缺失里剔出来**：不剔的话，每次离线几分钟再同步都会被判成缺口，
走全量重写 2400 行——虽然不慢，但报告会一直显示「回补」，掩盖真正的异常。

**秒级**：`ticks` 只能本机采集，公开源没有历史秒级。体检只统计最近 30 分钟点数，
最新点超过 `max(3 分钟, 2×刷新间隔)` 就立刻补一次实时报价；历史空洞如实写「无法回溯补齐」，不伪造。

**源站上限**：单周期最多 1023 根。1m ≈ 2 个交易日、5m ≈ 9 天、15m ≈ 27 天，
所以 7 天的 1m 缺口可能补不全；报告里给 `coverage` + `note`，写明「1 分钟线实际覆盖起点」。

接口形状（`onSync` 返回）：

```json
{ "ok": true, "fetched": 128, "healed_bars": 5, "healed_items": 1,
  "check": {"days":7,"scanned":18,"missing":5,"gaps":1,"cleared":0,"forced":false,"incremental":128},
  "ticks": {"points":412,"age_sec":42,"refilled":true},
  "coverage": {"AL|1m": 1762xxxxxxx, "...": 0},
  "message": "体检回补 5 根 / 1 组 · 新增 128 根 · 本地 日线 5313 …",
  "note": "秒级仅本机采集（最近 30 分钟 412 点）…；1 分钟线实际覆盖起点 11-08 09:00（受源站 1023 根上限）" }
```

前端另加勾选「强制全量重写近 7 天」，走 `N.syncHistoryForce(true)`，仅用于数据错乱时手动兜底。

  比对版本 `85` → 完成 `100`。`Bridge` 转成 `onUpdateProgress{phase:"check"}`。

## 2026-11-11（补）Web 页面「已断开 重连中」根因与修复（后端热修）
- **现象**：浏览器打开 `http://180.76.238.232:8123` 右上角常显「已断开，重连中…」，每 4 秒重连一次。
- **根因**：`backend/app/main.py` 的 `/ws` 端点 `_origin_allowed()` 只允许
  `localhost/127.0.0.1/::1`，经公网 IP（或 LAN IP/域名）访问时浏览器 `Origin: http://180.76.238.232:8123`
  不在白名单，服务端 `ws.close(1008)` 拒绝 → 前端永久重连。服务器日志实锤：`ws 拒绝非本机 Origin: http://180.76.238.232:8123`。
- **修复**：`_origin_allowed(origin, host)` 新增比对请求 `Host` 头主机——**Origin 主机与本次请求 Host 主机一致即放行**，
  公网 IP / 局域网 IP / 反向代理域名均可建立 WS，本地 `localhost` 仍兼容。
- **验证**：服务端 venv `websockets` 客户端以 `Origin=http://180.76.238.232:8123` 连 `ws://180.76.238.232:8123/ws`
  返回 `CONNECTED`（recv 13KB tick）；重启后 `journalctl` 不再出现「ws 拒绝」。已 scp 重部署并 `systemctl restart`，commit `ea2c430` 推送 main。
- **说明**：纯后端热修，未改 App 二进制，不上新 APK / 不动 version.json。
