# 学记期货 · futures-forecast

手机 App（学记期货）＋ Python 研究后端两件套。

App 端**完全独立运行**：直连新浪公开行情，把秒级快照、分钟线、日线落进手机 SQLite，
在本地算指标与七周期（1m / 5m / 15m / 30m / 4h / 8h / 1d）方向，界面为移动优先的深色/白天双配色，
行情支持 1 秒 / 30 秒 / 1 / 5 / 15 / 30 / 60 分钟 / 日线共 8 个周期、十字星与三品种涨跌幅对比，
带预测留档与命中率统计，并可从私有仓库自助更新（带下载进度条）、可选接入 DeepSeek 等大模型做多周期分析。

后端是本仓库的量化研究工具（岭回归 + 前向验证），用于回测与调参，App 不依赖它。

下面三个品种的实时采集与方向预测逻辑两端同源（App 端为七周期 1m/5m/15m/30m/4h/8h/1d）：
**电解铝（沪铝主力 AL0）**、**氧化铝（沪氧化铝主力 AO0）**、**伦铝（LME 3M AHD）**。

数据全部来自公开接口，无需任何 API Key。

## 一、能做什么

| 能力 | 说明 |
|------|------|
| 实时行情 | 每 3 秒抓取一次最新价 / 买卖价 / 成交量 / 持仓量 |
| 秒级数据累积 | 公开接口给不到历史秒级数据，服务把每次抓取自建为秒级快照库 |
| 多周期 K 线 | 1 分钟原始 + 5/15/60 分钟本地聚合 + 多年日线 |
| 六周期预测 | 走向外验证的岭回归 + 动量融合，输出方向、上涨概率、预期幅度、目标价、验证胜率 |
| 量化指标 | RSI、MACD、ATR、布林带位置、波动率、区间位置、EMA 多空排列 |
| 资讯聚合 | 东方财富全文检索（电解铝 / 氧化铝 / 伦铝）+ 同花顺 7×24 快讯按关键词过滤 |
| 趋势建议 | 综合六周期评分给出方向建议，并提示超买超卖、波动率、多周期分歧等风险 |

## 三、数据来源与粒度（重要）

| 品种 | 实时 | 1 分钟历史 | 日线历史 |
|------|------|-----------|---------|
| 电解铝 AL0 | 新浪 `nf_AL0` | 约 1023 根（≈3 个交易日） | 2005 至今 |
| 氧化铝 AO0 | 新浪 `nf_AO0` | 约 1023 根 | 2023-06 至今 |
| 伦铝 AHD | 新浪 `hf_AHD` | 当日分时 | 2016 至今 |

**关于“秒级一年历史”**：公开接口不提供秒级历史，付费源（天勤 TqSdk / CTP / Wind）才有。
本项目采取两条腿走路：

1. 运行即累积——每 3 秒一条快照存进本地 SQLite，跑得越久秒级历史越长；
2. 分钟线兜底——1 分钟粒度可回溯约 3 个交易日，日线可回溯多年，足以支撑 8 小时与 1 天周期的建模。

## 四、预测模型

每个 (品种 × 周期) 独立训练：

1. **特征**：标准化收益率、EMA 比值、RSI、MACD 柱、布林 Z 值、ATR 占比、20 期波动率、量比、时间趋势项；8 小时周期不再拼接分钟级特征块（与 1 天同样仅用日线序列）。
2. **目标**：未来 N 根的**对数收益率**，1% 分位缩尾去极值。
3. **验证**：前 70% 训练、后 30% 走向外验证（`_FOLD_FRACTION = 0.30`），报告真实样本外方向胜率。
4. **融合**：岭回归权重与其验证胜率挂钩（胜率 ≤50% 时权重为 0），剩余权重给动量持续性；若两个信号都没有验证优势，自动收缩输出并报“震荡”，避免用掷硬币的准确率给出自信的错误结论。
5. **概率**：用验证残差标准差把融合信号映射为正态 CDF，得到上涨概率。
6. **综合**：六周期按置信度加权投票得到看涨 / 中性 / 看跌，并生成带风险提示的建议文本。

> 8 小时与 1 天共用日线基准序列（A 股一个完整交易日含夜盘约 8 小时），两者在特征窗口和动量权重上不同。

### 历史数据与同步

发版前用 `scripts/build_seed.py` 抓一份真实行情打进包里（不做任何合成）：

| 周期 | 根数（每品种） | 覆盖范围 |
|------|---------------|----------|
| 日线 | 沪铝 5313 / 氧化铝 821 / 伦铝 2537 | 2005 / 2023 / 2016 至今 |
| 60 分钟 | 1023 | 约 195 天（可覆盖「最近 180 天」） |
| 30 / 15 / 5 / 1 分钟 | 各 1023 | 100 / 56 / 17 / 4 天 |

设置页「同步历史数据」与官方源做**增量**合并：只把「本地最后一根及之后」的 bar 写库
（boundary 那根会被替换刷新），重复点击不会重复写库，结果回显每周期「新增根数 + 本地总量」。
日常不需要点它——采集循环每 60 秒就自动做一次同样的增量（日线 30 分钟一次），
这个按钮只是用来一次补齐 180 天窗口。
源站每周期最多返回 1023 根，因此 1 分钟线只能覆盖最近几个交易日；**秒级点公开接口不提供历史，
只能由 App 运行时累积**（保留 30 天），预置包里不含伪造的秒级数据。

> **预置库导入的两个坑（v2.1.2 修复）**
> 1. `seed_meta.version` 是 12 位时间戳（`202611092054`），旧代码用 `Integer.parseInt` 解析必然
>    `NumberFormatException`，被 catch 成 0 后直接判定「无需导入」——1.9 万根 K 线从未进过手机库，
>    于是装完曲线一直「等待数据」。现改为 **long 解析**。
> 2. 首次导入失败后没有自愈：现在只要本地 `kline` 为空就强制导入一次（`INSERT OR IGNORE`，不覆盖新数据）；
>    另加「ATTACH 失败则逐行写入」兜底与 `assets/seed_ver.txt` 版本旁文件（命中就不再拷贝 1.5MB）。

### 曲线交互与多周期大模型（v2.2.0）

**周期**：新增 `1秒` 与 `30秒`。两者都来自本机 `ticks` 表——`1秒` 是原始采集点连线，
`30秒` 按 30 秒时间桶聚合为 OHLC。注意采集频率取决于「自动刷新间隔」（默认 30 秒），
所以默认设置下 1 秒视图实际也是 30 秒一个点，图下会标注「采集点」，不做假的 1 秒行情。

**十字星**：按住图表横向拖动，竖线吸附到最近数据点，右侧显示该位置价格、底部显示时间，
左上角列出该时刻的 开/高/低/收 与区间涨跌幅；松手后保留 2.5 秒淡出。

**三品种对比**：三品种价格量级差 8 倍（约 20380 / 3126 / 2612），直接叠加会压成一条线，
因此对比模式统一换算成「窗口首点 = 0%」的涨跌幅，纵轴单位是 %；图例同时给出最新价与区间涨跌幅，
点图例可单独隐藏某条曲线。单品种模式仍按红涨绿跌着色。

**大模型七周期**：模型输入包含现价、七档量化结论、技术指标、六个周期的统计摘要
（区间涨跌 / 最高 / 最低 / 平均振幅 / EMA5-20 关系）与最近 40 个采集点；
输出 `horizons[]` 固定 7 个 key（1m/5m/15m/30m/4h/8h/1d），每个含方向、置信度、目标区间与一句话依据。
落库时逐周期写入 `forecasts`（`source='llm'`，到期时间按 1/5/15/30/240/480/1440 分钟），
历史页可分别统计各周期命中率。量化模型的档位同步改为这 7 档（4h/8h 由 60 分钟线聚合）。

### 实时跟随、增量落库与预测调度（v2.3.0）

**曲线跟随最新**：`1m/5m/…` 的 K 线只到上一根收盘，所以前端会把最新报价接成序列尾部的点，
每个采集周期曲线都走到现价。脚注第二行显示`最新 价 · 时间`；超过 `max(2×刷新间隔, 2 分钟)`
没有新数据会标黄并写「滞后 N 秒」（日线不参与，日线时间戳是交易日期）。
按住十字星时曲线**冻结**不重绘，松手 2.5 秒后自动补上冻结期间到达的数据。

**增量落库**（不再是整段 1023 根覆盖）：

| 数据 | 频率 | 写库口径 |
|------|------|----------|
| 秒级点 `ticks` | 每次采集（默认 30 秒） | 一条一个 `(code, ts)`，同秒重复只覆盖 |
| 1 分钟线 | 每 60 秒 | 只写 `ts >= 本地 MAX(ts)`（含 boundary 那根，正在走的 K 线也在动） |
| 5/15/30/60 分钟 | 每 60 秒 | **由 1 分钟线本地聚合**（按时间桶对齐），再按各自水位增量补 |
| 日线 | 每 30 分钟 | 只写最后一根及之后 |

好处：每轮请求从 15 个降到 3 个（每品种 1 个），5/15/30/60 分钟口径与 1 分钟天然一致，
重复执行零新增行（`scripts/check_incremental.py` 会断言这一点）。

**预测刷新**：

- 自动：独立调度器**对齐每个整分钟（:00 秒）**——整分钟只重算 1m/5m/15m/30m 四档，
  整点（`:00` 分）先增量补数据再全量重算七档；
- 手动：预测页「更新预测」按钮，先增量补数据（分钟线 + 日线）再全量重算，带 3 步进度条，
  完成后回显「新增 X 根 · 七档方向已重算」；
- 面板下方常驻「上次更新 / 下次自动」时间，避免用户不知道它在自己跑。

产物：`releases/futures-forecast-v2.3.0.apk`（约 3.1 MB，已签名，minSdk 24）

装好后无需任何配置即可看到行情；要大模型分析就在「设置」填 API Key，
要 App 内自助更新就在「设置」填 Gitee 个人令牌。

### 体检式同步与全链路进度条（v2.4.0）

「同步历史数据」不再无脑追尾：先对最近 **7 天**做完整性体检，再决定补还是只增量。

| 情况 | 判据（以源站序列为基准逐根比对） | 动作 |
|------|--------------------------------|------|
| 中间空洞 | 源站有、本地没有，且早于本地最后一根 | 该周期近 7 天窗口整体 REPLACE 回补 |
| 整段清空 | 本地近 7 天 0 根而源站有数据 | 同上，全窗写回 |
| 正常尾部 | 源站有、本地没有，但晚于本地最后一根 | 只写尾部（原增量口径） |
| 完好 | 无空洞无清空 | 仅增量到最新 |

- 逐根比对源站序列，不自建交易日历 → 夜盘、周末、节假日不会误判成缺失。
- 秒级（ticks）不回溯：只校验最近 30 分钟是否还在进点，最新点过期立即补一次实时报价。
- 报告写清体检结论（扫描组数 / 空洞根数与段数 / 清空组数）、秒级点数与**实际覆盖起点**；
  受源站 1023 根上限，1m 约 2 个交易日，7 天的 1m 空洞补不全时会如实标注。
- 设置页新增勾选「强制全量重写近 7 天」，仅数据错乱时手动用。

更新链路也补全了进度反馈：点「检查更新」立刻出现进度条（读发行版时不确定态，解析到 release 后转确定），
无新版落成灰色完成态，有新版直接续成下载进度；下载显示 `1.9 / 3.0 MB · 947 KB/s · 剩余 1 秒`；
下载完 100% 保持并提示「正在调起系统安装器」；失败时轨道染红、按钮变「重试更新」直接重下，无需重新检查。

## 八、版本与自动更新

版本号规则：`versionCode = 主*100 + 次*10 + 修订`（2.3.0 → 230），Release 正文首行标注 `versionCode: 230`。

**更新源固定为 Gitee（首要源）**：App 内「设置 → 应用更新」带令牌读取本仓库 `releases/latest`，
比较 `versionCode` 后下载并调起安装。令牌只存手机端（AndroidKeyStore 加密），不上传任何服务器。

> **为什么必须走附件 API（v2.1.1 修复 403）**
> 私有仓库的发行版直链 `https://gitee.com/zpj100/futures-forecast/releases/download/v2.1.1/xxx.apk`
> 无论带 `Authorization: token` 头还是 `?access_token=` **都返回 403**（该地址要浏览器登录态 Cookie）。
> 唯一可用路径是附件接口：
>
> ```
> GET https://gitee.com/api/v5/repos/{owner}/{repo}/releases/{release_id}/attach_files/{attach_file_id}/download?access_token=xxx
> ```
>
> 它 303 跳到 `foruda.gitee.com` 的临时签名地址，客户端需**手动逐跳跟随**（Java 默认自动跳转会丢参数）。
> `attach_file_id` 与文件体积只能从 `/releases/{id}/attach_files` 列表取——
> `releases/latest` 的 `assets` 里既没有 id 也没有 size。

`release/version.json` 保留为可读的版本清单，便于脚本或第三方读取：

```json
{
  "version": "2.5.0",
  "versionCode": 250,
  "url": "https://gitee.com/zpj100/futures-forecast/releases",
  "notes": "…"
}
```

发新版流程：改 `android/app/build.gradle` 的 `versionCode` / `versionName`
→ `bash android/build-apk.sh` → 更新 `release/version.json` → 提交并打 tag（`v2.5.0`）

### 分批补全的能力边界（实测源站）

`InnerFuturesNewService.getFewMinLine?type=N` 固定返回 1023 根，`num/count/datalen/start/end/date/scale` 均无效，
无历史分页接口，`getMinLine` 也不接受日期参数。按 `type` 切换才有更长历史：1m≈2 交易日、5m≈15 天、
15m≈2 个月、30m≈3 个月、60m≈6 个月。因此 **1m 的 7 天前空洞不可补**，App 不插值不伪造，
报告逐周期给出真实覆盖起点；5m/15m/30m/60m 可补满近 7 天。

## 十、v2.6.0：手机数据库修复 · WSL 服务端 · 双向同步

### 解决的三件事
1. **手机「同步历史数据」显示无缺失/新增 0 根**：根因是回补基准被 7 天窗口截断（源站 5m≈15 天、60m≈6 月的历史全被排除），外加旧版本「自然桶派生 vs 源站段末」双时间戳残留。
   - 回补基准改为**源站整段序列**（`buildBatches` 收集 `j.bars` 全部中本地没有的 ts），5m/15m/30m/60m 补到源站可给最长历史，1d 回溯 180 天，1m 仍 1023 根上限。
   - 首次启动**自动迁移**：`Engine.start()` 后台调用 `Store.migrateLegacyBars()`，对照 `assets/seed.db` 删除 5m/15m/30m/60m 的旧口径残留行（键 `db_migrated_260` 保证只跑一次）。
   - 设置页新增「诊断」与「重建本地数据库」按钮兜底。
2. **WSL 服务端启动与手机可达**：提供 `run-lan.sh`（内部 `FF_HOST=0.0.0.0` 监听），配合 Windows 侧 `netsh interface portproxy` + 防火墙放行 8123；手机填 `http://<电脑局域网IP>:8123` 即可（详见 `docs/11_手机数据库同步与修复.md`）。
3. **手机↔服务端数据库双向同步**：服务端新增 `/api/db/{status,export,import}`（独立分表 `kline_app`，不影响既有接口）；App 设置页新增「数据库同步」区块，双向增量、分批 ≤300 根、失败批续跑、幂等，含进度条与本地/服务端对照。

## 十一、v2.7.0：服务端化与启动自检（端口 8123）

### 解决的四件事
1. **服务端成为唯一真源**：把 App 核心能力（行情/预测/历史/设置）搬至 Web 前端 `backend/app/static`（四 tab 全覆盖），Android 端保留为独立 App 并默认指向 `8123`；后端时间序列统一毫秒整数、自然时间桶口径。详见 `docs/12_服务端化与启动自检.md`。
2. **启动自检补全**：新增交易日历 `backend/app/calendar.py`（日盘 9:00–15:00 含休市子窗口、夜盘 21:00–次日 01:00 跨午夜、跳过周末）与 `backend/app/autofill.py`，服务启动时按交易日历逐段比对 1m 覆盖率，窗口内缺失自动回补、窗口外（Sina 1m 固定 1023 根物理不可补）如实标注，且不阻塞 API 启动。
3. **服务端大模型**：新增 `/api/llm/config`（GET/POST，密钥存 `DATA_DIR/llm.json` 并 `chmod 600`，绝不入仓/库）与 `/api/llm/analyze`，复用七档预测生成趋势研判。
4. **预测命中率历史**：`collector` 每轮把七档预测落库 `forecast_log`（主键幂等），新增 `/api/history` 按 horizon 统计命中率（对应周期到期后有实际价可比对，短周期数分钟内即可出数）。
